# 計測ロジックのリファクタリング方針

## 目的と範囲

現行 `ProductMonitoring` の取得・保存・販売状態判定の責務を明確にし、振る舞いを維持しながら変更しやすくする。表示・通知・集計は影響先として確認する。従来の `Crawl` と商品設定の統合は対象外とする。[desc] [Q1] [Q2] [Q3]

## 現状と課題

- `Crawler` は URL ごとの取得、ページ制限、重複排除、フィルター、取得状況の構築を担い、サイト実装も価格解析などを逆参照する。取得結果と出品はハッシュで受け渡され、必須項目や欠落の意味は呼び出し側に分散する。
- `SyncCrawlResults` は取得、保存、条件外削除、サイト固有の売り切れ同期、詳細確認の依頼を調整する。販売状態の判断は同クラス、`DetailCandidates`、`CrawlDetailJob` に分かれ、取得元の失敗や上限到達による違いを追いにくい。
- 出品の同一性は取得と集計では `external_id`、表示では `platform` と `external_id`、DB の一意制約では設定と `external_id` を用いる。サイト間の ID 衝突時に結果が欠落する可能性があるが、実被害は未確認であり修正は別途合意する。
- 条件外削除と集計は対象行を Ruby 側で選別する。規模拡大時の負荷は未計測であり、今回の優先目標には含めない。

## 要件

- **FR1**: 既存の取得元、ページ数・時間制限、取得失敗時の部分成功、検索条件を維持する。既存テストと追加の振る舞いテストで確認する。[desc] [Q2]
- **FR2**: 出品保存、除外状態、条件外削除、売却日保持と詳細確認の現行動作を維持する。取得元の失敗・打ち切り・価格なし・3時間境界を含むケースで確認する。[desc] [Q2]
- **FR3**: 一覧取得、取得結果の解釈、保存・販売状態の更新、詳細確認の境界を追えるよう整理する。各サイトの違いと共通の判断を識別できること。[Q3]
- **FR4**: API、ジョブ引数、DB スキーマ、表示・通知・集計への影響を調査し、変更が必要な場合は別途提案し合意する。[Q1] [Q2]
- **NFR1**: 外部取得の URL 制限、プロキシ、タイムアウト、ログの秘匿方針を維持し、取得失敗を成功に見せない。[desc] [Q2]
- **NFR2**: 変更前後に対象テストを同じ Compose 環境で実行し、差異を調査する。DB の更新とジョブ投入の境界を含めて検証する。[desc]

## 設計候補

### 候補 A: 現行構成を保ち、責務を段階的に整理する（推奨）

既存サイトクラスと Sidekiq の入口は維持する。まず取得結果・取得元の状態のハッシュの意味をテストと説明で明示し、次に一覧の販売状態反映と消失判定を保存処理から分ける。詳細確認候補は現行の別クラスを維持し、共通化が明確な判断だけをまとめる。既存の Active Record とトランザクションを使い、新しい共通基盤は設けない。

利点は変更単位とレビュー範囲が小さく、段階ごとに現行動作と比較できること。欠点は当面ハッシュと DB 依存が残り、境界の型による保証は限定的なこと。

### 候補 B: 取得結果・販売状態の契約を値オブジェクトで明示する

候補 A の分離に加え、取得元の成功・失敗・打ち切りと出品情報を明示的な値として扱う。無効な組み合わせを減らし、各サイトから保存処理までの契約を追いやすくする。一方、全サイトとテストの変換が必要で、一度に変更する範囲が広がる。現在必要な項目と不変条件が固まった段階で必要性を再評価する。

## 移行・検証方針

1. 実装前に対象 spec のベースラインを Compose の `backend` で取得し、失敗を記録する。対象は crawler、各サイト、同期、詳細ジョブ、設定更新、集計・表示の関連テストを含む。
2. 差異が表れやすいケースを既存テストで確認し、欠ける場合だけ振る舞いを固定するテストを追加する。成功・部分失敗・未対応 URL・打ち切り、重複、価格なし、除外、販売中への復帰、売却日の保持、3時間境界、詳細ジョブを対象にする。
3. 一覧の販売状態判定など、独立して比較できる範囲から小さく移す。各段階で DB の更新内容とジョブ投入を確認し、変更前後のテストを比較する。MySQL 固有の upsert やトランザクションの実動作もコンテナで確認する。
4. 対象 API と表示・通知・集計に影響がないこと、ログと Datadog / BugSnag に影響がないことを確認する。必要なら正本文書を更新する。各段階は独立して差し戻せる変更単位とする。

## 制約と未決事項

- 実装は方針のすり合わせ後に行う。挙動変更・既存データ修復・ID の一意制約変更は今回の承認に含めない。[desc] [Q2]
- URL、ページ取得の完全性、状態遷移をどの単位で表現するかは実装計画で具体化する。候補 A は提案であり決定ではない。
- `updated_at` が出品変更日時と詳細確認間隔の両方に使われる点は、現行動作を前提として確認する。意味を分けるスキーマ変更は別途合意する。
